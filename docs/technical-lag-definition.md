# Как считаем technical lag

Версия 1, 05.10.2026. Этот документ нужен, чтобы при сборе датасета мы одинаково считали отставание зависимостей. Реализации расчета здесь пока нет.

## Что считаем одной строкой

Одна строка — требование к одной прямой зависимости из `package.json` конкретной версии пакета: имя пакета, его версия, имя зависимости, тип зависимости, строка требования и момент наблюдения `t`. Например, `app@1.0.0` → `lib: ^1.0.0`. Для первого среза `t` равно времени публикации `app@1.0.0`. В дальнейшем можно брать тот же манифест на более поздние даты; новую версию `app` считаем отдельно.

В основной анализ берем только `dependencies`. `devDependencies` нужны в основном для разработки, `peerDependencies` разрешаются в окружении потребителя, а `optionalDependencies` могут не установиться. Эти три типа сохраним в данных, но если захотим их изучить, посчитаем отдельно. Если одно имя есть и в `dependencies`, и в `optionalDependencies`, считаем его optional и исключаем из основного анализа: [npm пишет, что optional запись имеет приоритет](https://github.com/npm/cli/blob/latest/docs/lib/content/configuring-npm/package-json.md#optionaldependencies).

По манифесту мы не знаем, какая версия реально установлена. Поэтому ниже «используемая версия» означает максимальную версию, которую разрешает требование на дату `t`. На реальную установку могут повлиять lockfile, `overrides`, платформа и настройки npm. В анализе уязвимостей это тоже нужно писать явно: речь пока о потенциально разрешаемой версии, а не о подтвержденной установленной.

## Какие версии были доступны на дату t

Берем полный ответ npm Registry для пакета зависимости: `versions` и `time[version]`. Сокращенного ответа для расчета дат недостаточно; поля полного ответа описаны в [документации Registry](https://github.com/npm/registry/blob/main/docs/responses/package-metadata.md). Для версии потребителя нужны ее манифест и `time[consumer_version]`.

Из сохраненного ответа оставляем версии, которые есть в `versions`, имеют корректный стабильный SemVer и опубликованы не позже `t` по `time[version]`. Время сравниваем в UTC, равенство включаем. Prerelease (`-alpha`, `-beta`, `-rc` и т. п.) в основном расчете не участвуют. `time.created`, `time.modified` и нынешний `dist-tags.latest` для выбора версии не используем. Версия потребителя тоже должна быть стабильной и с известной датой публикации.

Срез можно считать только если оба ответа Registry получены не раньше `t`. Если у какой-либо стабильной версии пакета зависимости нет корректного `time[version]`, строку исключаем: неизвестная дата может поменять ответ. Исходные ответы, время их получения и версию парсера сохраняем, чтобы результат можно было повторить. Для сравнения версий и диапазонов используем `semver@7.8.4` с `loose: false`, `includePrerelease: false`, без `coerce` ([правила node-semver](https://github.com/npm/node-semver#readme)).

Это приближение к историческому состоянию Registry. Мы отсекаем релизы после `t`, но версия, которую позже сняли с публикации, уже может отсутствовать в сегодняшнем ответе. Прошлые значения `dist-tags` и дату deprecation он тоже не показывает. Поэтому помечаем такие срезы `reconstructed_survivors`; точная реконструкция потребует архивных снимков или событий Registry. npm отдельно описывает [unpublish](https://docs.npmjs.com/unpublishing-packages-from-the-registry/) и [события publish/unpublish/deprecate](https://github.com/npm/registry/blob/main/docs/hooks/hooks-payload.md).

## Как выбираем версии и считаем lag

Пусть `C(t)` — стабильные версии зависимости, доступные к `t` по правилам выше. Тогда:

- `v_req` — максимальная по SemVer версия из `C(t)`, которая удовлетворяет требованию из манифеста;
- `v_latest` — максимальная по SemVer версия из всего `C(t)`.

Максимум определяется номером версии, не датой релиза. Если `C(t)` пусто или требованию не подходит ни одна версия, lag не равен нулю: строка остается без метрик с причиной исключения. Если у двух версий из `C(t)` одинаковый SemVer precedence, но разные строки (например, различается только `+build`), строку тоже исключаем как неоднозначную.

Считаем три показателя:

1. `version_lag` — число стабильных версий из `C(t)`, которые больше `v_req` по SemVer. Это счет релизов, а не разница чисел в номере версии.
2. `time_lag_days = (time[v_latest] - time[v_req]) / 86 400 000`, если время хранится в миллисекундах. В данных оставляем дробное число дней без округления. При одинаковых версиях lag равен 0. Если автор позже опубликовал версию с меньшим номером, разница может быть отрицательной; сохраняем ее и ставим `nonmonotone_publish_order=true`.
3. Тип доступного обновления: `major`, если отличается major; иначе `minor`, если отличается minor; иначе `patch`, если отличается patch; иначе `none`. Можно хранить это как три взаимоисключающих флага `major_available`, `minor_available`, `patch_available`. Это сравнение с самой новой версией, а не перечень всех промежуточных обновлений.

`time_lag_days` — разрыв между датами публикации двух версий. Он не показывает, сколько дней автор пакета фактически не обновлял lockfile. Для временного анализа отдельно можно считать возраст первой возможности обновиться: `t - min(time[v])` среди версий `v > v_req`; если таких версий нет, он равен 0.

## Как читаем version constraints

Используем правила [node-semver](https://github.com/npm/node-semver#readme), а не свой парсер:

| Запись | Как обрабатываем |
| --- | --- |
| `1.2.3`, `=1.2.3` | Только эта версия. Если к `t` ее нет, строка без метрик. |
| `^1.2.3` | Версии от `1.2.3` до `2.0.0` не включительно. Для `^0.2.3` верхняя граница `0.3.0`, а не `1.0.0`. |
| `~1.2.3` | Версии от `1.2.3` до `1.3.0` не включительно. |
| `>=1.0.0 <2.0.0`, `1.0.0 - 2.0.0`, `||` | Интервалы и их объединения разбирает node-semver; выбираем максимальную подходящую версию. |
| `*`, `1.x`, `1.2.*`, `1`, `1.2`, пустая строка | Wildcard и сокращения по node-semver. `*` и пустая строка разрешают все стабильные версии, поэтому при непустом `C(t)` lag равен 0. |
| Явный prerelease в требовании, например `^1.2.3-beta.1` | В основной анализ не берем; сохраняем для отдельного среза, чтобы не смешивать стабильные и prerelease-релизы. |
| `latest`, другой tag, `npm:` alias, Git, `file:`, URL | Не берем: это не обычный SemVer-диапазон, а историческое разрешение tag из текущего ответа не узнать. |

Обрезаем только пробелы по краям требования. Некорректные диапазоны не исправляем автоматически. Некорректные номера версий пропускаем и отдельно считаем, сколько их было.

## Примеры для проверки

Предположим, `app@1.0.0` опубликован 01.03.2026 в 00:00 UTC и содержит `dependencies: {"lib": ...}`. У `lib` есть только эти стабильные релизы, тоже в 00:00 UTC: `1.0.0` — 01.01, `1.1.0` — 11.01, `1.1.1` — 21.01, `2.0.0` — 01.02, `2.1.0` — 11.02, `2.1.1` — 21.02. Значит, на дату публикации `app` самая новая версия `lib` — `2.1.1`.

| Требование | `v_req` | `version_lag` | `time_lag_days` | Обновление |
| --- | --- | ---: | ---: | --- |
| `1.0.0` | `1.0.0` | 5 | 51 | major |
| `^1.0.0` | `1.1.1` | 3 | 31 | major |
| `~1.1.0` | `1.1.1` | 3 | 31 | major |
| `>=1.0.0 <2.1.0` | `2.0.0` | 2 | 20 | minor |
| `*` | `2.1.1` | 0 | 0 | none |
| `2.1.0` | `2.1.0` | 1 | 10 | patch |

Например, для `^1.0.0` подходят релизы серии `1.x`, поэтому берем `1.1.1`. После него вышли три стабильные версии, а между 21 января и 21 февраля прошел 31 день. Отдельный пример для `0.x`: если есть `0.2.3` (01.01), `0.2.5` (11.01), `0.3.0` (21.01), то при `^0.2.3` на 01.02 получим `v_req=0.2.5`, `version_lag=1`, `time_lag_days=10`, тип `minor`.

## Когда строку исключаем

Причину сохраняем вместе с исходным требованием и снимками. Чтобы два разработчика выбрали одну причину при нескольких проблемах, проверяем в таком порядке:

1. Нет стабильной версии потребителя или ее даты публикации — `invalid_consumer_version_or_time`.
2. Это не `dependencies` — `unsupported_dependency_type`.
3. Требование не SemVer, содержит явный prerelease или не разбирается — соответственно `unsupported_requirement`, `prerelease_requirement`, `invalid_requirement`.
4. Нет ответа по зависимости, либо любой из двух снимков получен до `t` — `missing_dependency_snapshot`, `snapshot_before_t`.
5. У стабильной версии зависимости нет корректной даты — `incomplete_release_history`.
6. На дату `t` нет стабильных версий — `no_available_stable_version_at_t`.
7. Есть две версии с одинаковым SemVer precedence — `ambiguous_semver_precedence`.
8. Диапазону не подходит ни одна версия — `no_satisfying_version_at_t`.

У исключенной строки метрики остаются `NULL`, а не 0. Deprecated-версии не исключаем: текущую пометку можно сохранить вместе с датой получения ответа, но нельзя считать, что она уже действовала на историческую дату. Unpublished/retracted-версию, которой нет в снимке, восстановить из него нельзя. Количество исключений по причинам нужно показывать вместе с итоговыми результатами.

## Что обсудить на review

Нужно согласовать с командой три решения: оставить ли только `dependencies` в основном анализе, подходит ли приближенная реконструкция истории для первого датасета и как формулировать выводы об уязвимостях без lockfile. Пока действуют правила, записанные выше. Примеры и даты проверены вручную; замечания второго участника добавим сюда после review.
